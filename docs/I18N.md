# Interface localization

`src/ui/i18n.ts` owns language state and the English/Spanish catalogs. English remains the initial language unless the existing browser preference is Spanish. Storage-denied browsers can change language for the current session.

- `getLanguage()` and `setLanguage('en' | 'es')` select the language.
- `subscribeLanguage(callback)` updates Preact shell subscriptions without rendering musical surfaces.
- `t(id, parameters)` resolves a stable catalog entry with named interpolation.
- `translate(en, es)` bridges genuinely dynamic legacy pairs.
- `translateDOM(root)` updates **known** static control labels and accessibility attributes in place. Call after a panel renders and after explicit language changes. There is no mutation observer and no replacement of control subtrees.
- `translateText(text)` is for known plain labels in new component integrations.

The DOM bridge excludes user-owned names, clip options, preset names, launcher cells, waveform regions, version lists, note blocks and musical keys. It never changes input values. New controls should use `t()` or explicit `data-i18n`; user content should be marked `data-user-content`.

## Migration tool

Run `node scripts/migrate-i18n.mjs --source src/app.ts --output /tmp/i18n-app.ts` once against unmigrated source. It generates bilingual JSON catalogs and a transformed file without editing the original. Literal `L(en, es)` calls become `t(id)`. Template pairs are migrated only when interpolated expressions match in both languages, preserving their evaluation semantics. The remaining dynamic `L()` calls should use the `translate` bridge.

The transformer uses Prettier's TypeScript parser because the installed TypeScript 7 compiler package does not expose the classic compiler API. It requires the existing Prettier development dependency, not a runtime parser dependency.

Integration requires `resolveJsonModule: true` in TypeScript and a JSON-aware bundler (Vite). Import `t`, set language before controller rendering, and replace local language helpers with the central service. Add new messages to both catalogs; catalog keys must match. Generated IDs depend on source English wording and are not user-facing.

## Validation

Catalog key parity, interpolation parity, source transformation parsing and DOM exclusions should be checked when modifying the localization layer. Do not infer translation completeness from the existence of the DOM bridge: component-authored labels should use explicit catalog IDs.
